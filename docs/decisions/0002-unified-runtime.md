# ADR-0002：统一运行内核、显式生命周期与步骤恢复

- 日期：2026-10-12
- 状态：P4 复核后纳入实施基线；未实现；后续细化见 ADR-0004/0005
- 关联：G-02、G-03、G-05；Q-API-01/02/03/04/06/07

## 背景

P1 的 API 草案未明确便利调用暂停、流断开、跨进程恢复和资源释放的含义。同一功能若分别由 SDK 和服务实现，容易出现规则偏差。

## 决定

- 使用一个异步 Runtime，提供 start/wait/订阅/响应/取消/恢复；便利 API 组合这些操作。
- Runtime 拥有执行任务，取消等待不取消任务；显式关闭要处理活动调用并报告无法安全关闭的情况。
- Agent.run 是无持久化交互的临时配置，遇到交互返回 interaction_unavailable；Agent.run_sync 仅在没有活动事件循环的线程使用。
- 持久化采用单进程排他所有权、同会话单个未结束 Run、顺序工具执行；先形成明确恢复边界。
- 关键状态、检查点和事件同事务提交。外部动作保存派发证据；未知写入需要核查，不承诺 exactly-once。
- 身份、审批和操作归属在内核校验。恢复绑定 Agent revision，重新查询权限与依赖。
- 多 Agent 先定义同 Runtime 的顺序子运行组合，不承诺复杂团队编排；P3 后续决定见 ADR-0004：延后，不纳入 v0.1。

## 替代与代价

- 让每种入口自带循环：实现初期方便，但后续规则容易分裂。
- 让便利入口自动创建本地持久化文件：能保留暂停，但引入隐含文件与身份管理，不采用为默认值。
- 首期并行工具和多 worker：吞吐量可能更高，但审批、恢复及状态协调面显著扩大；后续独立引入。
- 把普通 trace 当恢复日志：观测的采样、导出失败与数据保留不适合承载执行正确性。

选择的代价包括：显式 Runtime 的使用概念、顺序工具的吞吐限制、运行存储写入开销和更严格的版本管理。上述成本必须在实现后测量，不预先宣称性能领先。
