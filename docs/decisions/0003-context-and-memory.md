# ADR-0003：可检查的上下文与显式提交的内置 Memory

- 日期：2026-10-12
- 状态：P4 复核后纳入实施基线；未实现；后续细化见 ADR-0004/0005
- 关联：G-04、G-05；Q-API-05

## 背景

P1 确定了上下文和记忆可检查的方向，但尚未定义记忆检索何时生效、“已保存”意味着什么，以及多个用户之间如何隔离。

## 决定

- 每次新的模型调用先生成并保存 ContextManifest，记录来源、版本、选入/排除与处理方式；同一次调用重试使用相同输入。
- required 检索等待到明确期限，失败即停止这次模型调用；best_effort 在预算内读取，迟到结果不插入已经发出的调用。
- 首期 Memory 使用 Runtime 的内置事务存储，按租户、用户、Agent 隔离；会话之间可共享但 Agent 之间不默认共享。
- 写回采用显式 memory 工具，写入和工具成功结果原子提交；应用单独配置权限。首期不在回复后隐式启动自动提取和写回。
- 默认以确定性裁剪为基础；P3 后续决定将模型摘要移至后续版本，届时也必须显式启用；上下文保护部分超预算时提前失败。
- 调试导出与恢复必需数据分开；删除当前记忆不会伪称历史记录和备份也已清除。

## 替代与代价

- 默认后台提取/写回：可能更方便，但完成时点、成本及失败反馈更难解释；留给后续明确任务协议。
- 任意 Memory 后端直接套用同一保证：无法保证跨库事务；后续适配必须显式描述一致性与恢复。
- 全局共享记忆：接入简单，但会混淆用户、Agent 和会话边界，不作为默认行为。
- 永远等待检索：信息更完整，但增加延迟；提供 required 和 best_effort 两种有明确语义的选择。

内置 Memory 的保证会限制第一版适配范围，也可能增加本地存储量。ContextManifest 有额外存储和脱敏责任；通过记录粒度与保留策略控制，不无条件保存全部可见内容到外部平台。

## 规范位置与复核

详细装配、作用域与提交规则在 [行为契约](../planning/runtime-contract.md) 第 7 节；B-08、B-09、B-10、B-15 是后续测试依据。第一版是否产生有效记忆仍需任务评测，事务成功不代表模型记住了正确内容。
