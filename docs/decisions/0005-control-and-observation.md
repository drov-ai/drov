# ADR-0005：控制提交、查看权限与结束后的历史

- 日期：2026-10-13
- 状态：P4 实施基线；未实现、未做运行测试
- 关联：细化 ADR-0002/0003/0004；API 与运行契约升为 v3，未增加首期能力类别

## 背景

沿三个场景复核时发现，P3 中“保存响应后继续”“订阅遇到暂停结束”等表述不足以确定并发行为。响应回执已返回但状态仍是旧审批，会让 resume 立即返回错误快照；重放历史暂停也可能提前结束流。正文权限只在维护策略中出现，各入口缺少一致投影。失败后的会话历史及限额耗尽后的核查也需要明确规则。

## 决定

1. 响应消费、回执、检查点、事件和后续状态同事务提交。需要继续执行时先预留活动槽位，提交后状态已是 running；容量/配置不满足不消费请求。重复响应先查回执，再判断新响应的期限，不重复派发。
2. start 先授权及去重，再检查会话/容量；没有无界持久任务队列。取消、响应和终态通过版本条件更新竞争。
3. 事件补读只有追平当前暂停/终态才结束，历史旧暂停不终止新的 running 阶段；补读与实时订阅消除漏读窗口。事件游标与列表游标分开定义。
4. 默认 inspection/events/context 返回元数据，正文需显式请求及 view_content。便利入口会返回正文，必须在接受新执行或响应前预检；只有控制权限的人可使用 respond。失败和取消也保留已知/未知用量。查看投影不改写恢复记录或伪造类型化结果。
5. 会话保存已提交的完整消息事实，失败/取消为未派发调用留下明确结束结果；不完整流不入历史，未知事实不改写成成功，终态与历史投影原子提交。
6. 限额/取消停止新的 Agent 工作，未知写入仍需核查。提供 verify 入口调用应用的只读 verifier，返回建议但不消费请求；它具有单独控制期限和审计，不能绕过权限、容量和恢复 barrier。核查建议最终仍通过 respond 消费原请求。取消/限额收尾只要求可信效果证据，不强求已无法取得的业务输出。
7. 未停止的旧调用仍占资源，suspended 不能当作已安全释放。核查期限仅提醒，不让未知效果因过期而永久失去提交证据的入口。

## 替代与代价

- 将响应接收和运行推进拆成两套最终一致流程，需要额外调度队列、客户端状态和恢复规则；首版选择 Runtime 槽位加本地原子提交。
- 每个 SDK/HTTP/UI 入口自行脱敏，容易遗漏 token 或交互参数；选择内核共享授权投影，代价是 DTO 需区分正文是否可见。
- 取消/预算耗尽立即统一标终态更简单，但会丢失未知副作用；保留 reconciliation，需要用户在证据不足时处理暂停。
- verifier 自动判定并直接恢复更省一步，但混合证据获取与执行授权；首版返回建议，经显式响应统一消费。只读查询也必须有超时和资源限制。

不引入通用任务队列、完整事件溯源平台或新权限产品。以上规则属于已承诺的审批、持久化、检查和生命周期能力，具体代码组织仍由任务中的实现与测试决定。
