# 交付阶段与进入代码的条件

状态：P1 至 P4 的历史设计审查通过；当前实施状态与下一项只看 [progress](progress.md)。2026-10-14 按 ADR-0013/0016 增加首版代码与文件/产物、可选 E2B 任务，不重开一般规划。

## 四个规划阶段

| 阶段 | 需要完成的工作 | 退出条件 |
| --- | --- | --- |
| P1 产品与接口草案 | 产品定义、能力对标、API 草案、三类案例、证据与协作规则 | 文件可交叉引用；方向与提案区分清楚；下一轮问题有清单 |
| P2 架构与行为契约 | 模块边界、状态机、资源所有权、事件/检查点、上下文/Memory 时序、权限与交互、错误和恢复 | 首期相关 Q-API 问题有明确答案；三个案例按同一契约修订；关键决定形成 ADR |
| P3 质量与分期实施 | 收敛 v0.1、选择最小技术栈、测试与评测方案、依赖有序任务、发布及文档策略 | 每个首期能力映射到任务和验收；依赖与已知限制清楚；不依赖未准备的线上环境才能开始 |
| P4 一致性复核 | 从三个案例反查 API/架构/任务，检查来源和未决项，标记实施基线 | 所有代码就绪条件满足，留下明确首个实施任务和验证方法 |

阶段由交付物决定，不按日历机械推进。同一轮可以完成相邻阶段的独立工作，但不可跳过关键契约。完成 P4 后应进入代码，不为了规划本身继续制造文档。

## P2 的工作包与交付位置

1. 明确 Agent、Session、Run、Runtime、工具、Memory 和服务入口的依赖边界。
2. 画出正常运行、审批、补充输入、失败、取消、待核查和恢复的状态变化，确定检查点单元。
3. 区分持久化事件、展示事件和模型 token 增量，规定结果与事件关系。
4. 确定用户/租户/会话/记忆作用域，以及模型数据不能修改哪些控制信息。
5. 明确上下文装配顺序、预算、记忆读取/写回与内容记录策略。
6. 明确工具执行与外部结果未知的行为，不承诺通用 exactly-once。
7. 决定便利 API、流式入口、同步接口及资源退出的含义，更新全部示例。

已形成 [architecture.md](architecture.md)、[runtime-contract.md](runtime-contract.md) 和 ADR-0002/0003；P3 升级至 v2，P4 修正控制/查看/历史语义至 v3 并同步参考应用。检查结果与阶段完成状态在 [进度](progress.md)。

## P3 的具体工作包

1. 将 C-01 至 C-19 分成明确首期、首期实验性与后续范围；对多 Agent、Skill、沙箱及应用扩展服务给出理由。
2. 选择最低 Python、schema 支持、模型适配器、MCP 传输、存储/锁实现、包结构及默认限额；避免在同一轮引入多个等价库。
3. 形成离线、协议集成、故障注入、真实模型任务评测和人工体验验证的分层方案。
4. 把首期每个 C、S/X、B 要求映射到可独立交付的任务，明确依赖、输出与完成条件。
5. 制定数据记录/脱敏/保留、兼容/迁移、许可证与上游复用、版本发布和文档更新规则。
6. 写清真实模型测试前需要的模型服务、Key 配置及预算方式；这些材料不阻塞离线实现任务。

已交付：[首期范围](capability-matrix.md)、[工程方案](engineering.md)、[质量计划](quality-plan.md)、[有序任务](implementation-plan.md)、[维护发布策略](release-policy.md) 和 ADR-0004。P4 的逐项就绪证据见 [实施基线](implementation-baseline.md)。

## P4 的具体工作包

1. 从 S-01/02/03 正常与失败路径反查 API → Runtime → 存储/工具/Memory → 验收和任务，修正矛盾、缺项与不必要的首期复杂度。
2. 检查 scope/权限、未知写入、数据库提交取消、HumanInput、Memory 版本、内容清理与旧备份恢复；重点复核 P3 新增边界。
3. 核对每项首期承诺均有任务和完成条件；B-14 等后续能力不得混进首期就绪或宣称测试通过。
4. 分清代码前必须明确的契约，与代码阶段实测才能确定的依赖 patch、性能及模型质量；把外部发布/Key 条件保留到对应任务。
5. 逐项给出 R-01 至 R-06 的证据和结论，留下有日期的实施基线与变更规则，明确首个代码轮 T-01。

P4 已完成上述工作，修正结果、六项就绪结论及 T-01 交接见实施基线。当时未提前实现 SDK；此为历史 P4 退出结论，后续实施事实见 progress，不机械增加规划轮次。

## 代码就绪条件

| ID | 条件 | 需要的证据 |
| --- | --- | --- |
| R-01 | 产品方向和 v0.1 范围清楚 | 产品定义与能力表一致，首期/后续边界已标记 |
| R-02 | 首期公共 API 契约能覆盖三个案例 | 草案中的关键问题已处理；片段不互相矛盾；后续变化有记录方式 |
| R-03 | 状态、持久化、权限、资源和故障行为有明确设计 | 架构与行为契约、关键 ADR、错误路径验收要求 |
| R-04 | 质量计划能够检验实现 | 离线测试、集成测试、真实模型评测分层；样本、断言、预算方式和报告限制明确 |
| R-05 | 开发工作可以按依赖逐步实施 | 任务含能力 ID、输入、交付、验收及前置依赖，首个任务无需猜测 |
| R-06 | 最小工程与复用策略明确 | Python/依赖/包布局、许可选择或受控复用规则、版本与发布路径有决定；不含真实凭据 |

就绪检查只证明“有足够的实施基线”，不证明设计绝不会改变。真实模型 Key、最终域名、PyPI 名称和官网上线不必成为开始离线代码工作的阻塞项；若首个实现任务确实依赖外部资源，优先调整为可离线验证的任务。

## 开发阶段里程碑

M1 离线内核 → M2 上下文/Memory → M3 交互/恢复/代码执行 → M4 模型/MCP/HTTP/工作台 → M5 发布准备。唯一任务表、依赖图与 21 张任务卡（含必交 T-10A/T-10B、可选 T-10C）在 [实施计划](implementation-plan.md)，本文件不复制第二份排期。

多 Agent 延至 v0.2 候选，Skill、更多沙箱深度、调度/渠道按独立场景排期；Docker Python/受控文件/持久产物按 [ADR-0016](../decisions/0016-sandbox-artifacts-and-backends.md) 纳入首版必交，E2B 为独立可选适配；知识工具案例首期交付。后续版本按缺陷、使用反馈和评测证据选择，不要求每次 release 都新增大模块。

## 后续每轮的完成定义

- 交付对应文件或实现，回查相关目标与能力。
- 运行适当验证，说明验证了什么、没有验证什么。
- 同步源文档、受影响示例和进度，不把聊天当成唯一决策记录。
- 给出下一轮具体目标、交付物和完成条件。

进入代码后，规划可以基于证据修订。影响核心契约的修改需先更新决定及验收，再修改实现，避免以代码现状倒推没有记录的产品要求。
