## 已确认方案做到什么

依据 [C-17](../planning/capability-matrix.md)、[API 草案](../planning/api-draft.md)、[运行契约第 13 节](../planning/runtime-contract.md)、[工程第 9 节](../planning/engineering.md) 和 [任务卡](../planning/implementation-plan.md)：

| 维度 | 当前 T-10A/T-10B 承诺，尚未实现 |
| --- | --- |
| Agent 闭环 | 模型产生 Python code，沿现有审批在真实一次性 Docker/Linux 环境执行，实际结果回同一模型循环，最终输出沿 Agent codec 校验；代码错误可成为后续新代码操作 |
| 审批与归属 | 宿主决定后端/镜像/限额；批准绑定原代码/hash/配置与 tenant/user/Agent/Run/operation；默认 ask，可显式 allow；计算批准不批准业务写入 |
| 结果 | 有界 stdout/stderr、实际 exit_code/termination/截断事实；工具拿到错误结果不表示代码成功；没有独立文件产物通道 |
| 环境 | 每操作新容器/工作目录，默认标准库；宿主可以预构建依赖镜像并固定/验收，模型不能现场安装依赖；容器内可有临时文件/子进程 |
| 隔离与限额 | 非 root、有效 seccomp、禁止提权/外连/宿主挂载/凭据；实际 CPU/内存/PID/工作盘/输出限额，不能只比参数字符串 |
| 生命周期 | 取消/超时停止整个容器进程树；确认停止/销毁后收尾，清理不明保留租约/名额/SQLite 所有权；按原执行键核查，不重新执行已派发代码 |
| 恢复 | 恢复 Run 的已提交语义边界和原结果/资源清理；不恢复 Python 变量或 Notebook，也不把重启后的重算叫恢复 |
| 尚未包含 | 用户文件直接输入、生成文件持久输出、跨调用共享沙箱状态、独立 Bash/文件工具工作区、代码仓库/浏览器环境、云后端、任意联网；普通 Python/MCP 工具仍在其宿主边界 |

T-10A 负责真实闭环，T-10B 负责完整隔离/资源/取消/故障/恢复矩阵，两卡不能互相代替。工程 10s/512MiB/1 CPU/64 PID/64MiB 工作盘/64KiB code 与输出/并发 2 是起始默认，不是所有计算任务的绝对产品边界；具体配置仍由宿主在管理限制内选择。只有代码参数的方式适合小型计算、规则/文本/JSON处理；需要对真实 CSV 分析、生成图表或交付文件时，缺少标准数据进出通道会限制实用性。这是基于接口的设计判断，不是用户试用实验。

## 核实的外部事实

AgentScope 取 **Python v2.0.9**，tag 经 GitHub API 核实为 commit `2e706a6fa66813646e0d267e13757b5dbe912359`，不混用 Java、Runtime 独立项目或 main。官方 Workspace 概览列出 Docker、E2B 等后端、Bash/文件工具、Skill/MCP 和上下文卸载；固定源码的 E2BBackend 封装 commands.run 与文件读写。E2BWorkspace 初始化按 metadata 连接/创建，关闭采用 pause 来保留工作区。它的范围超过单次 Python 执行；这些事实不证明其所有恢复/隔离行为优于 Drov，没有进行同条件实测。来源见证据 E-29。

E2B 的官方滚动文档说明托管 Linux VM、文件读写、代码解释器的图表/多种结果、code contexts 和文件系统/内存 pause/resume；具有按用量计费、账户限制及费用上限机制。沙箱默认允许外连，默认公共服务可访问性需要按具体 API 显式收紧。metadata/filter、sandbox ID 和 kill 是可利用的机制，不能由此推出创建幂等、取消已确认或 Drov 的一次派发保证。具体 SDK/模板/构建版本和真实能力尚未锁定或验收。来源见 E-30 至 E-33。

## 推荐的调整（待确认）

结论：当前方案的生命周期/故障验收深度足够严肃，任务使用面偏窄。建议补齐数据与产物，再用独立可选后端任务引入 E2B。对标通用能力仍然成立，不将 CSV/图表等验证样本改成产品业务边界。

1. **首期必交受控输入与产物输出。** 由宿主/用户显式授予已归属的数据对象，向一次性工作区复制有大小/数量限额的输入；审批固定代码与输入版本/hash。不让模型指定任意宿主路径，不通过 host bind mount 实现。输出在销毁工作区前有界提取/持久提交，以归属、opaque 引用、内容 hash、类型/大小和独立授权读取；防路径穿越、符号链接、特殊文件和输出风暴。先验收 CSV/JSON/文本及固定依赖镜像生成的 PNG 等实际例子，具体公开格式与默认额度在确认后由源文件定义。不能把 stdout 截图或模型自述当成文件产物。
2. **执行工具与后端分离。** 保持模型侧 Python 执行工具一致，将后端生命周期/执行句柄/查证/清理与 Docker 特有字段分离。必要内部接口随真实 Docker 实现落地；不预建 E2BSandbox 空壳或许多没有后端的抽象。后端声明/验证实际能力，缺条件接收前拒绝。Docker 的 seccomp/PID/tmpfs 等机制不能硬套成每个云提供商都支持的同名字段。
3. **E2B 作为首期系列的独立可选适配目标。** 建议接在 T-10B 后，独立任务卡及实验性 extra；候选编号/依赖在采纳后确定，本轮不创建 T-10C 卡。第一版只做相同的单次 Python/受控文件/有界结果、显式查询和销毁，默认禁代码外连/公共服务；不顺带开放持久 Notebook/任意 Shell/联网安装。支持声称以真实远端验收为准，无账号/预算时不把模拟测试写成 E2B 支持，也不让可选云集成阻塞 Docker 首版。若用户要求正式首版上线即能云端执行，应明确把该任务改为必交并同步发布门槛。
4. **继续延后持久交互工作区。** 跨调用变量/文件共享、长驻进程、快照/fork、Session pause/resume、代码仓库与浏览器环境涉及新的共享归属/并发/取消/数据保留语义，建议第二阶段独立验收。E2B 提供这些基础机制不等于 Drov 已经正确集成。首期可以逐次把明确授权的前次产物作为新操作输入，仍保持每次执行隔离；这不等于恢复旧 Python 状态。

有依赖的计算能力不必等到云后端：当前设计已经允许宿主预构建带 numpy/pandas/matplotlib 等库的镜像。若将数据分析镜像列为首期内置支持，还需实际版本锁、许可、镜像指纹和资源/安装/场景验证，不能只扩大说明中的库名。

## 若采纳，须同时变更的工作

文件/产物增加公共输入/输出及持久数据归属，E2B 增加可选依赖、远端控制与费用边界；应形成新简短 ADR，再同步 capability-matrix、API、runtime-contract、architecture、engineering、三个案例的代码变体、quality-plan、implementation-plan、release-policy 和 progress。HTTP/UI/维护/备份/清理应保护同一批输入与产物引用，不能另开一套授权/存储；新 sandbox schema 只在对应真实实现时生成。

推荐先把 T-10A/T-10B 修改为包含受控输入/产物的 Docker 闭环与故障卡，再确定可选 E2B 卡。若拆成单独数据卡，也须明确首版是否依赖它；不能用“小范围优化”偷偷取消原安全条件或将新必交项留在验收之外。新增工作量不只一个 provider 类，本轮不编造实施天数。

E2B 实测前需要用户提供/确认：账户及可用服务/区域、可固定的模板/构建与权限、`E2B_API_KEY` 的本地凭据引用、可上传的合成代码/数据、并发/寿命限制、独立沙箱费用上限（与模型预算分别记账）。Key 只在本地环境或凭据管理配置，不进聊天/Git/模型/沙箱。读取官方资料不需要这些资源，本轮没有调用其付费 API。
